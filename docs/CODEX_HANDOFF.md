# FATE EXECUTOR / 命运执行者 — Codex 项目交接说明

> 本文面向接手项目的 Codex。它描述当前本地工作区中实际可运行的版本，而不只是最初的 GDD。开始任何开发前，仍须阅读 `README.md`、`DEVLOG.md`、`docs/ARCHITECTURE.md`、相关源码和全部测试，并以测试与当前实现为准。

## 1. 项目概览

《FATE EXECUTOR / 命运执行者》是一款使用真实扑克牌构筑的 Roguelike 卡牌游戏，使用 Godot 4.x 与 GDScript 开发。

核心体验是：

- 玩家经营一副由独立卡牌实例组成的永久牌库。
- 战斗中从真实牌堆抽牌，选择 1～5 张组成扑克牌型。
- 伤害由计分牌点数与牌型倍率共同决定。
- 玩家可局部刷新手牌，围绕对子、顺子、同花等牌型组织战术。
- 战斗后通过金币、删牌、加牌与饰品逐渐改变整局 Build。
- 每完成一个节点，从三个独立随机生成的节点中选择下一站。

项目仍标记为 **v0.1**。当前本地工作区已经超过最初战斗 Vertical Slice，包含基础局内推进、奖励、三节点地图和特殊节点，但尚未形成完整商业版本。

## 2. 当前可玩游戏循环

```text
新游戏
→ 第 1 关普通战斗
→ 胜利奖励
→ 生成下一关的 3 个节点
→ 选择并确认 1 个节点
→ 完成普通战斗 / 精英战斗 / 商店 / 泉水 / 宝箱
→ 关卡 +1
→ 再次生成 3 个节点
→ 循环
```

当前节点包括：

- **Battle / 普通战斗**：使用当前关卡成长后的欠筹赌徒。
- **Elite / 精英战斗**：暂用相同敌人行为，生命、攻击和奖励提高。
- **Shop / 商店**：删牌、五选一买牌、治疗和购买饰品。
- **Fountain / 泉水**：免费恢复最大生命的 30%。
- **Treasure / 宝箱**：打开后三选一饰品，打开前可以放弃。

所有节点完成后使用同一套全局关卡推进逻辑。第 1 关固定从教学普通战斗开始，第 2 关起显示三节点选择。

## 3. 当前扑克牌规则

### 3.1 基础牌库

- 新游戏拥有标准 52 张扑克牌，不含大小王。
- 每张牌都有唯一 `instance_id`。
- 当前没有万能牌和特殊效果扑克。
- 四种花色在数据中使用固定 ID。
- 新牌奖励可以与已有牌重复点数和花色，但必须获得新的实例 ID。

### 3.2 点数

- 2～10：牌面数字。
- J = 11。
- Q = 12。
- K = 13。
- A = 14，且始终为最高点数。

顺子允许 `10-J-Q-K-A`，不允许 `A-2-3-4-5`，不允许环绕，也不能把 A 临时解释为 1。

### 3.3 牌型优先级与倍率

| 优先级 | 牌型 | 倍率 | 计分牌 |
|---:|---|---:|---|
| 9 | Straight Flush / 同花顺 | ×3.00 | 构成牌型的 5 张牌 |
| 8 | Four of a Kind / 四条 | ×2.75 | 相同点数的 4 张牌 |
| 7 | Full House / 葫芦 | ×2.50 | 全部 5 张牌 |
| 6 | Flush / 同花 | ×2.25 | 全部 5 张牌 |
| 5 | Straight / 顺子 | ×2.00 | 全部 5 张牌 |
| 4 | Three of a Kind / 三条 | ×1.75 | 相同点数的 3 张牌 |
| 3 | Two Pair / 两对 | ×1.50 | 两组对子的 4 张牌 |
| 2 | Pair / 对子 | ×1.25 | 对子的 2 张牌 |
| 1 | High Card / 单张 | ×1.00 | 所选牌中点数最高的 1 张 |

计算方式：

```text
基础攻击力 = 计分牌点数总和
牌型伤害 = 基础攻击力 × 牌型倍率
```

未被判定为计分牌的已选卡牌不加入基础攻击力。最终结果使用项目现有的统一取整规则。牌型配置位于 `data/poker_hands.json`，判定由 `PokerEvaluator` 负责。

## 4. 当前战斗规则

### 4.1 战斗区域

每张战斗卡牌实例必须且只能位于一个正式区域：

- `DRAW_PILE`：牌堆。
- `HAND`：手牌。
- `DISCARD_PILE`：弃牌堆。

`BattleDeckState` 是区域所有权的唯一领域对象。真实牌堆顶部位于数组尾部，抽牌使用 `pop_back()`。任何 UI 排序都不得写回真实牌堆。

### 4.2 开局、出牌与补牌

- 战斗开始时将当前永久牌库复制为本场战斗卡牌状态并确定性洗牌。
- 初始从牌堆抽到 8 张手牌。
- 玩家每次判决必须选择 1～5 张牌。
- 规则层拒绝第 6 张牌，不只是 UI 阻止。
- 判决只打出已选择的牌；已打出的牌进入弃牌堆。
- 未选择的牌继续保留在手中。
- 敌人行动结束且双方存活后，从牌堆补牌至 8 张。

这条“保留未打出的手牌”规则覆盖早期“判决后弃掉全部八张牌”的设计。

### 4.3 刷新

- 每场战斗有 3 次刷新。
- 每次刷新当前选择的 1～5 张牌。
- 刷新的牌进入弃牌堆，未选择的牌保留。
- 从牌堆补回相同数量的新牌。
- 刷新不结束玩家回合，不触发敌人行动，也不改变敌人意图。
- 每次成功刷新固定消耗 1 次，无论刷新几张。
- 刷新后清除选择并重新按显示规则排序。

刷新是同步领域事务：规则层先一次性确定弃牌、抽牌、重洗与最终手牌，动画只播放结果，不在回调里调用随机数。

### 4.4 抽牌不足与重洗

所有抽牌都经过 `BattleDeckState.draw_to_hand()`：

1. 从真实牌堆顶部抽牌。
2. 牌堆不足时先抽完剩余牌。
3. 将完整弃牌堆移入牌堆并清空弃牌堆。
4. 使用同一战斗 RNG 流洗牌。
5. 继续抽到所需数量或所有可用牌耗尽。

手牌中的牌不参与重洗。若牌堆与弃牌堆仍不足，不会复制实例；系统返回所有可用牌、记录错误并允许手牌暂时少于 8 张。

### 4.5 排序与浏览

- 手牌仅在 UI 上按点数从左到右递减，A 在最左侧方向，2 在最右侧方向。
- 同点数手牌按花色 ID 升序：`Clubs → Diamonds → Hearts → Spades`。
- 牌堆与弃牌堆浏览器按花色分行：`Spades → Hearts → Clubs → Diamonds`。
- 每一行按 `A → K → ... → 2` 显示；同牌重复实例按 `instance_id` 升序。
- 浏览顺序是只读副本，不改变真实抽取顺序，也不消耗 RNG。

## 5. 玩家与敌人

### 5.1 玩家局内状态

- 初始最大生命：100。
- 初始当前生命：100。
- 初始金币：0。
- 饰品槽：6。
- 最小永久牌库：20 张。
- 生命、金币、永久牌库和饰品跨节点保存。

### 5.2 普通敌人成长

当前普通敌人是 **Debt Gambler / 欠筹赌徒**。关卡属性由配置公式集中生成：

```text
health = round(35 + 5 × (stage - 1) + 0.12 × (stage - 1)²)
attack = min(40, round(5 + 0.55 × (stage - 1) + 0.015 × (stage - 1)²))
```

关键值：

| 关卡 | 生命 | 攻击 |
|---:|---:|---:|
| 1 | 35 | 5 |
| 5 | 57 | 7 |
| 10 | 90 | 11 |
| 15 | 129 | 16 |
| 20 | 173 | 21 |
| 30 | 281 | 34 |

生成记录包含 `stage`、`base_health`、`final_health`、`base_attack`、`final_attack` 和 `enemy_type`。

### 5.3 精英投影

- 精英最大生命 = 同关普通敌人生命 ×1.5 后取整。
- 精英攻击 = 同关普通敌人攻击 ×1.5 后取整。
- 精英金币与奖励概率也应用 ×1.5，概率上限为 100%。
- 当前精英仍复用欠筹赌徒行为，并不是完整的独立精英敌人系统。

## 6. 战后奖励

### 6.1 普通战斗

- 金币：均匀随机 5～15，胜利后自动领取一次。
- 删除一张牌：独立 40% 概率。
- 新饰品：独立 60% 概率。
- 五选一新牌：独立 80% 概率。

三项可选奖励彼此独立，不是三选一，因此可能全部出现或全部不出现。

### 6.2 删除牌

- 玩家可以领取或放弃。
- 删除前需要二次确认。
- 永久牌库不能低于 20 张。
- 删除后永久修改整局牌库。

### 6.3 饰品奖励

- 从未拥有的饰品池生成。
- 同名饰品不能重复拥有。
- 最多 6 个槽位。
- 满槽时必须明确选择要替换的旧饰品，不能自动替换。

### 6.4 五选一新牌

- 打开前可以放弃。
- 一旦打开即进入 `must_choose`，必须选择一张才能继续。
- 五张候选、候选实例 ID 和强制选择状态立即存档。
- 重启后恢复完全相同的候选，不重新随机。
- 当前候选只是普通标准扑克，不包含特殊效果或万能牌。

## 7. 地图与特殊节点

每次生成 3 个节点，三次概率判定相互独立，允许出现重复类型：

| 节点 | 概率 |
|---|---:|
| Battle / 普通战斗 | 35% |
| Shop / 商店 | 10% |
| Elite / 精英 | 20% |
| Fountain / 泉水 | 15% |
| Treasure / 宝箱 | 20% |

玩家选择节点后还需确认。确认前可取消，确认后其他两个候选失效。节点的候选、选择、确认、进入和完成状态均持久化。

### 7.1 商店

- 删除牌：15 金币，最多 2 次。
- 五选一买牌：5 金币，最多 3 次；付费打开后必须选一张。
- 恢复 30% 最大生命：20 金币，最多 1 次，只在实际能治疗时扣费。
- 饰品库存：6 件未拥有且互不重复的饰品。
- 饰品满槽时要求明确替换，取消不扣费。
- Black Wax Seal / 黑蜡封印在进入商店时生成价格快照，折扣 10%，最低价格 1；本次商店内购买它不会递归改价。

### 7.2 泉水

- 免费恢复最大生命的 30%。
- 不超过最大生命。
- 保存进入前生命、实际恢复量和恢复后生命。

### 7.3 宝箱

- 生成 3 件互不重复且未拥有的饰品。
- 打开前可放弃。
- 打开后进入强制选择，不能取消。
- 候选与 `must_choose` 状态即时存档。
- 饰品槽满时必须明确替换。

## 9. UI、本地化与交互约束

- 首次启动默认英文，可切换英文或简体中文。
- 所有可见文本从 `data/localization.json` 读取，禁止把完整双语字符串散落在 UI 脚本。
- 语言切换立即刷新当前界面，并保存到本地设置。
- 未选择卡牌悬停时只显示高光，不移动、缩放或改变布局。
- 已选择状态覆盖悬停状态；选中牌固定上移，不叠加悬停高光。
- 卡牌视觉状态优先级：禁用 > 已选择 > 未选择悬停 > 普通。
- 战斗中的 Rules / 规则详细页面只读，不暂停、不改战斗数据、不消耗随机数。
- 抽牌、弃牌、刷新和重洗动画只消费领域结果；动画不能决定抽到什么牌。
- 动画和结算期间使用输入锁，防止重复刷新、重复判决或重复结算。

## 10. 架构与数据流

项目保持低耦合、数据驱动结构：

```text
UI / Scenes
→ AppServices、Localization、Repositories
→ Run / Reward / Node 流程服务
→ Battle、Hand、Poker、Trinket 领域逻辑
→ BattleDeckState、Deck、CardData 与只读结果对象
```

关键原则：

- UI 不直接生成随机结果。
- UI 不直接决定卡牌区域归属。
- 领域命令一次性完成数据事务，再返回结果对象给动画。
- 浏览、预览和打开规则页面不改变 RNG。
- 手牌与牌堆的显示排序不修改领域数组。
- 配置与本地化尽量放在 JSON，不将关卡或概率硬编码成 UI 分支。

### 10.1 关键领域对象

- `CardData`：单张卡牌数据和唯一实例 ID。
- `Deck`：整局永久牌库。
- `BattleDeckState`：本场战斗牌堆、手牌、弃牌堆及洗牌 RNG。
- `HandSelection`：统一验证 1～5 张选择上限。
- `HandState`：出牌、刷新、补牌与选择状态。
- `PokerEvaluator`：九种牌型、计分牌和伤害计算。
- `BattleState`：玩家/敌人生命、护盾、行动与胜负。
- `RunState`：关卡、生命、金币、永久牌库、饰品和未完成流程。
- `RewardState` / `RewardGenerator`：一次胜利奖励快照及独立奖励随机流。
- `NodeState` / `NodeGenerator` / `NodeFlowService`：地图候选与节点生命周期。
- `ShopState`：单次商店库存、价格快照、次数与未完成交易。
- `TreasureState`：宝箱候选与强制选择。
- `TrinketRuntime`：饰品战斗与治疗效果。

### 10.2 关键数据文件

- `data/deck.json`：52 张基础牌与 A=14。
- `data/poker_hands.json`：牌型优先级、倍率和要求牌数。
- `data/enemies.json`：敌人成长公式。
- `data/rewards.json`：初始局内资源和奖励概率。
- `data/trinkets.json`：饰品价格、稀有度和效果参数。
- `data/nodes.json`：节点概率、精英、商店、泉水和宝箱配置。
- `data/localization.json`：英文和简体中文全部界面文本。

## 11. 存档与确定性随机

### 11.1 保存位置

```text
语言设置：user://fate_executor/settings.json
局内存档：user://fate_executor/run.json
```

`user://` 的实际系统路径由 Godot 决定，不应在业务代码中硬编码 Windows 用户目录。

局内存档包含关卡、当前/最大生命、金币、永久牌库、饰品、未解决奖励、地图节点、商店和宝箱状态。战斗中的临时牌堆顺序目前不写入局内存档。

### 11.2 RNG 边界

- 战斗牌堆拥有独立 RNG，洗牌和重洗继续使用同一流。
- 战后奖励使用独立奖励 RNG。
- 地图使用独立地图 RNG。
- 商店库存、付费候选和宝箱候选使用各自确定的种子或派生流。
- UI 浏览、规则页面、预览和确认操作不得偷取其他随机流的数值。

## 13. 测试与运行基线

最近一次记录的完整自动化基线：

```text
总数：1065
通过：1065
失败：0
跳过：0
```

该阶段同时记录了无头主场景启动和真实窗口渲染启动通过。

运行全部测试：

```powershell
godot --headless --path . --script res://tests/test_runner.gd
```

如果 `godot` 不在 PATH，可使用已安装的 Godot 4.x console 可执行文件。项目此前使用 Godot 4.7.1 验证。

每次规则修改至少应：

1. 运行相关领域测试。
2. 运行 `tests/test_runner.gd` 全量测试。
3. 运行无头主场景启动。
4. 对 UI 变更运行真实窗口渲染检查。
5. 更新 `README.md`、`DEVLOG.md`，架构变化时更新 `docs/ARCHITECTURE.md`。

## 17. 接手时必须注意

1. **先检查工作树。** 当前本地工作区包含大量尚未提交的阶段性修改，不能执行 `git reset --hard`、`git checkout --` 或覆盖式重建。
2. **不要把 GitHub 旧版本当作本地真相。** 本地三节点与特殊节点阶段可能尚未发布到远程。
3. **先读测试再改规则。** `tests/test_runner.gd` 是当前行为契约的重要组成部分。
4. **保持事务边界。** 随机结果由领域层一次性产生并存档，UI 与动画只消费结果。
5. **维护双语。** 新增可见文本必须同时提供英文和简体中文 key。
6. **维护唯一实例与区域一致性。** 不得为了补牌复制卡牌实例。
7. **保护预览纯度。** 实时伤害预览不能消耗饰品次数、改变 RNG 或提交战斗状态。
8. **不要提前开发。** 只完成用户当前阶段明确授权的系统。
